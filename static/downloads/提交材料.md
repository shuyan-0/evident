# 题目 08 · 投资事件情报与证据时间线 —— 提交材料

**产品名**：Evident
**一句话定位**：一个事件级证据溯源系统——帮用户看清同一投资事件的**最初来源、事实变化、证据冲突、当前状态与关注标的的关系**。

## 一、可访问、可实际操作的 Web 产品 URL

### https://a1e235b65284ebef9.app.workbuddy.host

- 打开即用，无需安装、无需登录。
- 已接入**扶摇真实数据**（`EVIDENT_DATA_MODE=real`），实测单次加载约 1.7~2.3 秒，缓存命中 0.03 秒。
- 操作路径：右上角输入关注标的（如 `600519.SH`）→ 点「刷新」→ 左栏选事件 → 中栏看证据时间线 → 右栏看证据冲突与关注标的行情。

### 核心能力（逐条对应题目）

| 题目要求 | 实现 |
|---|---|
| 事件最初来源 | 事件标题取"起点叙事"（最早的传闻/报道），时间线标注「◆ 最初来源」 |
| 事实变化 | 版本演化流；`披露时间 ≠ 更新时间` 时自动标记「发布后被修改」 |
| 证据冲突 | 冲突面板直连两条证据，按来源权重裁决（如公司回应 0.9 > 未署名传闻 0.06） |
| 当前状态 | 六态状态机：传闻中/已证实/已否认/已更正/已过期/存在冲突 |
| 与关注标的的关系 | 输入标的代码，相关事件置顶；展示行情与估值（仅关联展示，不构成建议） |
| 区分事实/观点/推测/传闻 | 每个证据原子带 `claim_type` 标注 |
| 体现证据权重 | 来源层级权重表（官方 1.0 → 未署名传闻 0.2），UI 可见 |
| 处理四种时间 | 每条证据显示：发生 / 披露 / 抓取 / 更新 + 披露滞后小时数 |
| 更新·否认·更正·过期改变结论 | 状态由**全量证据加权仲裁**得出（非取最后一条），且在主题子线索内独立裁定 |
| 结论可回溯原文 | 每条证据保留原始记录 ID 与原文链接 |
| 失败不静默 | 接口失败/降级/截断时页面顶部弹**显式警告横幅**并列出受影响接口 |

> 快讯的 `create_time_ms` 与 `update_time_ms` 是一对关键字段：两者不等即说明**该条信息在发布后被修改过**，为"版本演化"提供直接证据。

### 核心算法：事件归并（这是本题的真正难点）

普通做法按股票代码分组，会把"传闻 → 回应 → 公告"拆成三条独立记录，恰好丢掉题目要的"版本演化"。本系统采用**可解释规则归并**，并针对真实财经语料做了五重防误合并设计：

1. **主题锚点切分** — 同标的不同事项（收购传闻 vs 增持公告）必须切开
2. **jieba 分词 + 停用词** — 过滤"下跌/板块/公司"等高频套话
3. **代表点聚类（非并查集）** — 并查集有"链式传递"缺陷（A~B、B~C 相似会把无关的 A、C 也连成一簇，实测把 60 条无关新闻并成一条）；改为要求与**簇代表**达标才归入
4. **标题实体为主依据** — 标题信息密度高；仅用全文会让公司名拆分词（"贵州"/"茅台"）造成过合并
5. **权威口径豁免** — 官方公告措辞常与媒体差异极大（媒体"海外订单" vs 公告"重大合同"），对官方/公司口径在同标的+同主题时放宽门槛

每个归并都输出 `resolve_basis` 依据（标的、时间跨度、版本数、初始来源、聚类方式），**可审计**。

### 合规声明

- 不输出涨跌预测、收益承诺或买卖建议
- 事实/推断/不确定在 UI 上视觉区分（声明类型 + 来源层级标签）
- 所有结论可回溯至原始记录 ID 与原文链接
- API Key 仅经环境变量注入，不入仓库

## 三、候选人（人）修正的 AI 错误与不合理结果

以下问题均由**自测暴露后人工判定并修正**，是本次开发中最有价值的部分：

### 修正 1：事件过合并（AI 初版算法缺陷）

- **现象**：10 条记录被错误归并为 3 个事件，其中「白酒收购传闻」与「股东增持公告」
  被合并为同一事件（同标的、时间接近）。
- **AI 初版思路**：仅用 `标的重合(0.45) + 关键词 Jaccard` 计算相似度。
- **为什么不合理**：二者是同一标的下的**不同事项**，合并后事件语义混乱。
- **人工修正**：引入 **TOPIC_ANCHORS 主题锚点**（收购要约/股东增减持/重大合同/业绩财务/
  产品技术/监管合规/澄清回应）。两个都命中明确锚点且完全不重叠 → 判定为不同事件，相似度直接返回 0。
- **复测**：归并结果正确，事件标题恢复为「传某头部白酒企业将被产业资本要约收购」。

### 修正 2：状态机跨子线索污染（AI 初版逻辑缺陷）

- **现象**：白酒事件被标为「已更正」，但它其实应是「已否认」——因为更正记录属于"增持"子线索，
  而否认记录属于"收购"子线索。
- **AI 初版思路**：在**整个事件簇**上一次性仲裁状态（`有更正 → CORRECTED`）。
- **为什么不合理**：同一标的可能同时存在多条独立线索，跨线索仲裁会让一条线索的更正
  错误覆盖另一条线索的否认结论，违背"当前状态"的准确性要求。
- **人工修正**：改为 `_group_threads()` 先按主题锚点拆**子线索**，`_thread_verdict()`
  在每条子线索内独立仲裁，再取最需关注的结果作为事件状态，并标注"含 N 条独立子线索，已分别裁定"。
- **复测**：白酒事件正确显示「已否认」，理由为"官方口径否认（公司回应，权重 0.9）"。

### 修正 3：事件标题丢失起点叙事（AI 初版的呈现问题）

- **现象**：白酒事件显示为公告标题「控股股东增持计划实施完毕」。
- **AI 初版思路**：事件标题取**权重最高**的原子标题。
- **为什么不合理**：事件常以传闻开篇、以官方口径收尾。取最高权重会让事件失去
  "这是一个从传闻演化而来的事件"的关键信息，与「看清事件最初来源」的要求相悖。
- **人工修正**：改为优先取**最早的传闻/推测标题**（起点叙事），无弱信号时才取最高权重。
- **复测**：标题恢复为「传某头部白酒企业将被产业资本要约收购」。

### 修正 4：前端静默失败（AI 初版的健壮性缺陷）

- **现象**：以 `file://` 方式直接打开 `index.html` 时，页面**完全空白**，无任何提示。
- **为什么不合理**：直接违背题目「数据缺失、冲突、过期或调用失败时**不得静默生成正常结论**」。
- **人工修正**：`load()` 增加 `try/catch` 与 `fatal()` 分支，区分「协议为 file:」
  与「后端不可达」，显示明确原因 + 访问指引。
- **复测**：`file://` 下正确显示「无法获取数据：当前是以本地文件方式打开页面，未连接到后端服务」。

#### 修正 5：子线索分组取键错误（阶段一暴露）

- **现象**：增持公告与其更正记录本属同一线索，却被拆到不同线索，状态错判为「存在冲突」。
- **根因**：第一条公告正文含"不涉及控制权变更"，**同时命中 `{收购要约, 股东增减持}`**，
  而分组时用 `sorted(hits)[0]` 只取一个锚点，恰好取到"收购要约"，与只命中"股东增减持"
  的更正记录分了家。
- **人工修正**：改用**共享锚点连通（并查集）**分组，两个锚点集只要相交即同线索。

### 阶段二：接入扶摇真实数据后新增的修正

真实财经语料的复杂度远超构造数据，以下问题在接入后逐一暴露并修复：

#### 修正 6：异动解读淹没真实事件（数据配比失衡）

- **现象**：异动解读单次可返回 **3000+ 条**，截断后 160 条里 135 条是异动解读，
  个股新闻被挤掉，事件几乎全是"异动解读（大跌）：xxx"。
- **人工修正**：改为**按数据源独立配额**（新闻 75 / 快讯 30 / 异动解读 25），
  并把异动解读标题改用 `key_word_list` 构造以增强区分度。
- **复测**：个股新闻重回主体，出现多条真正的多来源事件。

#### 修正 7：n-gram 分词导致停用词失效（算法缺陷）

- **现象**：大量互不相关的异动解读仍被并成一条。
- **根因**：原先用滑窗 n-gram 提取片段，"异动解读（大跌）"被切成整体 token
  `"异动解读"`，而停用词表里是 `"异动"`/`"解读"` 两个词，**精确匹配无法命中**。
- **人工修正**：改用 **jieba 真实分词**，使"异动/解读/大跌"成为独立词并被停用词过滤。

#### 修正 8：并查集链式传递导致事件无限膨胀（最关键的算法缺陷）

- **现象**：接入真实数据后出现 **60 条**的巨型事件——"贵州茅台股王"、"百元酒当道"、
  "券商食品饮料观点"等无关新闻被并成一条，并产生 **97 个**虚假冲突。
- **根因**：并查集式聚类存在**链式传递**：A~B 相似、B~C 相似，则 A、C 也连通，
  即使二者毫不相关。财经新闻中"同标的 + 少量共词"极易形成这种链条。
- **人工修正**：改为**代表点聚类**——新记录必须与簇的**代表记录**（最早的、即"最初来源"）
  达到阈值才归入，从机制上杜绝链式膨胀。
- **复测**：巨型事件消失，归并结果变为 4~6 条精准多来源事件
  （如「中欧混动汽车磋商」= 财闻 + 凤凰网 + 中国基金报）。

#### 修正 9：公司名拆分词造成过合并（算法缺陷）

- **现象**：代表点聚类后仍有 28 条"比亚迪"巨型事件，混入"中欧贸易磋商""欧洲工厂"等内容。
- **根因**：jieba 把"贵州茅台""比亚迪"等公司名拆分，"贵州"+"茅台"两个词即可满足
  "共享 2 个实体"的门槛，而同标的下这些词高频出现，噪声极大。
- **人工修正**：**以标题实体为主要归并依据**（标题信息密度高、噪声小），正文实体降为辅助；
  并扩充停用词（加入"涨幅/较大/此前/局部/承压"等套话）。
- **复测**：28 条巨型事件降为 4~6 条精准事件。

#### 修正 10：官方公告与媒体报道无法归并（召回缺陷）

- **现象**：「公司公告：签订重大合同」与媒体「某算力龙头获海外大额订单」未能归并，
  本应是同一事件的两个阶段，却拆成两条。
- **根因**：官方公告的措辞与媒体差异极大（媒体"海外订单" vs 公告"重大合同"），
  标题层面**几乎无共同实体**，无法触发归并门槛。
- **人工修正**：对**权威口径**（`official`/`company`）记录增加豁免——同标的 + 共享主题锚点
  即可归并。理由是官方公告数量少、权重高，且是事件"被证实"的关键证据。
- **复测**：mock 归并恢复为正确的 4 个事件，测试 26/26 通过。

> 这 10 项修正全部由**人工判断并主导**：AI 负责实现，但问题识别、根因定位，
> 以及"用代表点而非并查集""以标题而非全文为主""对权威口径豁免"这类算法路线选择，
> 均出自人工判断。

## 四、AI 未参与的环节（人工独立完成）

| 截断标志（`was_truncated`）透传到 UI 层 | 上游截断不被隐藏 |

> 设计依据：扶摇官方文档明确「空列表也可能表示服务降级，不能据此断言期间没有异动」。

### 3. 接口失败（2 项）

| `auto` 模式无 key → 自动降级 mock 并带警告 | 降级行为对用户可见 |

## 性能测试（真实数据）

首屏需打 7 个上游接口，为此做了并行取数、特征预计算、TTL 缓存三层优化。

**各接口基线耗时（串行实测）**

| 接口 | 耗时 | 数据量 |
|---|---|---|
| 异动解读 | 1.79s | **4.2 MB**（最大瓶颈） |
| 个股新闻 600519.SH | 0.52s | 24 KB |
| 其余 5 个接口 | 0.16~0.18s | <25 KB |
| 串行合计 | 3.17s | |

**优化前后对比**

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 取数（7 接口） | 3.17s（串行） | 1.96s（并行） |
| 归并 + 仲裁 | 6.15s | **0.13s**（特征预计算） |
| **首次总耗时** | **8.77s** | **2.33s** |
| 缓存命中 | 无缓存 | **0.032s** |

**公网实测**

| 场景 | 耗时 |
|---|---|
| 首次加载（回源） | 1.69s |
| 缓存命中 | 0.42s |
| 强制刷新（`?refresh=1`） | 1.50s |

**关键验证点**
- 失败结果不写入缓存（避免把瞬时故障固化 90 秒）。
- `refresh=1` 可绕过缓存强制回源，页面「刷新」按钮即走此路径。
- `health.cache_hit` / `cache_age_s` 会透传到前端并显示，缓存状态对用户可见。
