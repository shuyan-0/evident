## 二、核心设计

### 数据流水线

```
Ingest(扶摇REST) → Atomize(证据原子) → Resolve(事件归并★) → Adjudicate(冲突/状态机) → Present(UI)
```

### 证据原子（核心数据单元）

| 字段 | 对应题目要求 |
|---|---|
| `claim_type`: fact / opinion / speculation / rumor | 区分**事实、观点、推测、传闻** |
| `source_tier`: official(1.0) / company(0.9) / media_major(0.7) / research(0.55) / media_general(0.4) / unattributed(0.2) | **证据权重**（权重表显式声明，UI 可见） |
| `event_time / disclose_time / fetch_time / update_time` | **四种时间**；`披露≠更新` 即"发布后被修改"的直接证据 |

### 事件归并（算法心脏）

普通做法按股票代码分组，会把"传闻→回应→公告"拆成三条记录，恰好丢掉"版本演化"。
本系统采用**可解释规则归并**，并针对真实财经语料做了三重防误合并设计：

1. **主题锚点切分** — 同标的不同事项（收购传闻 vs 增持公告）必须切开；
2. **停用词 + jieba 分词** — 过滤"下跌/板块/公司"等高频套话，避免仅凭这些词误并；
3. **代表点聚类（非并查集）** — 并查集存在"链式传递"缺陷（A~B、B~C 相似会把无关的
   A、C 也连成一簇，实测将数十条无关新闻并成一条）；改为要求与**簇代表**达标才归入；
4. **标题实体为主依据** — 标题信息密度高；仅用全文会让公司名拆分词
   （"贵州"/"茅台"）把大量无关新闻连在一起；
5. **权威口径豁免** — 官方公告措辞常与媒体差异极大（媒体"海外订单" vs 公告"重大合同"），
   对官方/公司口径在同标的+同主题时放宽门槛，保证关键确认证据能并入事件。

每个归并都输出 `resolve_basis` 依据（含标的、时间跨度、版本数、初始来源、聚类方式），可审计。

### 状态机（子线索仲裁）

```
RUMORED → CONFIRMED(官方证实) / DENIED(官方否认) / CORRECTED(更正) / EXPIRED(超期) / DISPUTED(冲突未消解)
```

状态由**全量证据加权仲裁**得出（非取最后一条），且在**主题子线程**内分别裁定——
避免"增持公告的更正"错误覆盖"收购传闻的否认"。子线索用**共享锚点连通**分组，
以正确处理同时命中多个锚点的记录（如"控股股东增持…不涉及控制权变更"）。

### 数据健康度（合规关键）

扶摇文档原文："空列表也可能表示服务降级，不能据此断言期间没有异动。"
因此接口失败/降级/截断（`was_truncated`）时 UI 顶部显示**显式警告横幅**，绝不静默生成"正常"结论。

## 三、AI 的角色

- AI（Claude）参与：架构设计、全部代码生成、mock 语料构造、联调自测与 2 处 bug 修复
  （①过合并→主题锚点；②状态机跨子线索污染→子线程仲裁）。
- 人在环：设计决策、验收标准、算法取舍（可解释规则优先于黑盒相似度）。
- 产品运行时**不使用 LLM 做结论生成**——所有归类/归并/仲裁均为确定性规则，保证可审计、可复现。

## 四、数据来源（已接入扶摇真实数据）

线上演示使用**扶摇真实数据**（`EVIDENT_DATA_MODE=real`），已实测跑通以下接口：

| 数据 | 接口 | 用途 | 关键字段 |
|---|---|---|---|
| 个股分时新闻 | `GET /api/news/stock/timeline-list` | **事件主来源** | `source` / `publish_time_ms` / `jump_url` |
| 快讯 | `GET /api/news/flash/list` | 高频演化跟踪 | `create_time_ms` **vs** `update_time_ms` |
| 异动解读 | `GET /api/news/anomaly/analysis` | 市场异动发现 | `first_publish_time` / `tag_code_update_time` |
| 行情快照 | `GET /api/a-share/prices/snapshot` | 标的关联展示 | `last_price` / `price_change_ratio_pct` |
| 估值 | `GET /api/a-share/valuations/snapshot` | 标的关联展示 | `pe_ttm` / `pb_mrq` |

> 快讯的 `create_time_ms` 与 `update_time_ms` 是一对关键字段：两者不等即说明
> **该条信息在发布后被修改过**，为"版本演化"提供直接证据支撑。

**认证**：`X-api-key` 请求头。Key 仅经环境变量注入，不写入仓库（`.gitignore` 已排除）。
iFinD MCP：沙箱内无凭据可调用，做适配器预留位，如实列为已知边界。

### 默认关注标的

未指定时默认分析 `600519.SH / 300033.SZ / 002594.SZ`；页面搜索框可替换为任意标的（逗号分隔）。

### 单次取数与配额

为避免某一类数据淹没其他来源，各数据源独立配额（可用环境变量覆盖）：
个股新闻 25 条/标的、快讯 30 条、异动解读 25 条（仅 A 股域）。
超配额时会在 `health.warnings` 中**显式提示被略过的条数**，不静默丢弃。

### 性能设计（响应时间实测）

首屏需打 7 个上游接口，为此做了三层优化：

| 优化 | 说明 | 效果 |
|---|---|---|
| **并行取数** | 7 个接口用线程池并发请求 | 3.17s → 1.96s |
| **特征预计算** | 归并是 O(n×簇数) 的成对比较，同一原子的 jieba 分词结果被反复使用；按 `atom_id` 缓存分词结果 | 归并阶段 6.15s → **0.13s** |
| **TTL 缓存** | 取数结果与行情/估值缓存 90 秒（`EVIDENT_CACHE_TTL` 可调） | 重复访问 **0.03~0.4s** |

实测（真实数据、120 条记录）：

| 场景 | 耗时 |
|---|---|
| 首次加载（回源） | **约 1.7~2.0s** |
| 缓存命中 | **约 0.03s**（本地）/ 0.4s（公网） |
| 点「刷新」（强制回源） | 约 1.5s |

失败结果**不缓存**，避免把瞬时故障"固化"90 秒。页面首次加载走缓存，点「刷新」强制回源。

## 五、已知边界与未做事项

- **线上为真实数据**：`EVIDENT_DATA_MODE=real`，接入扶摇 5 个接口；无 key 时按 `auto` 规则
  降级为构造数据并在 UI 显式告警，绝不伪造。
- 未做：研报观点库接入、LLM 语义级冲突检测（当前为线索词+数值口径+实体规则）、多用户/账号体系、演示视频。
- 归并为规则策略：真实语料下已针对链式传递、通用词、权威口径三类误合并做了专门处理，
  但复杂长尾场景仍需继续调参；低置信度归并已避免强合并（宁拆不并）。
- 上游偶发瞬时失败：已加**有限重试**（2 次，退避 0.8s），重试仍失败则如实标注 `failed`。
- 归并算法为 O(n×簇数)，已用特征预计算把归并阶段压到 0.13s；若把关注标的扩大到数十个，
  需引入向量化或索引（如倒排索引做候选召回），当前实现未做。
- 缓存为进程内内存实现，多实例部署时各实例独立缓存，未接 Redis。
